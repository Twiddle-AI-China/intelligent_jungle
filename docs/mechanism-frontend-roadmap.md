## 0. 一句话现状

系统「优于随机」目前**能证明的只有约束层**（和声菜单让任何落枝都在调内、四物种性格产生分工）；
**决策层**（economy 计分 → agent 计划 → master 叙事）的音乐增值目前是**断言，不是数字**。
本 roadmap 的主线 = 把「优于随机」从断言变成可复现的数字，然后按这个数字驱动机制打磨。

## 1. 【最高优先】核心逻辑验证：建「优于随机」评测器

**问题**：我们反复说系统「优于随机」，但从没量化过。每次改机制（张力偏置、H 耦合…）到底让音乐更好还是更差，全靠人耳盲猜。

**建议**：建一个 headless 评测 harness（mvp/eval/，与 gameplay 解耦），同一 world seed 跑三档并打分：
- **R 随机基线**：鸟随机落枝，无 economy/agent/master 决策（只保留和声菜单约束）。
- **C 仅约束**：和声菜单 + 物种性格本能，但 agent/master 不决策（规则/LLM 关掉）。
- **F 全系统**：现状（economy + agent + master + 张力偏置）。

**打分维度**（全部可从事件流离线算，不需人耳）：
- 和谐分 H'（已重定标）分布、行为分分布；
- 节奏规整度（落枝时刻对拍网格的贴合）、声部密度互补度（四声部同时发声的冲突/留白比）；
- 音高运动合理性（相邻发声音程分布，避免全跳进或全同音）；
- 可选：谱质心/RMS 平衡（复用 kimi2 已采样的电平口径）。

**验收 = 一张表**：F vs C vs R 每维度的数字，证明 F > C > R（或暴露某维度 F 不如 C，即决策层帮了倒忙）。
**这是所有后续机制改动的记分牌**——之后每个 PR 附「评测器数字变化」。

> 归属：这是纯新增目录（mvp/eval/**），文件边界不撞任何现有代码，适合独立派单。

## 3. 【架构评估】结论：不重写，只补执行器

**逐层体检：**
- **world → mapping → audio → renderer 分层 + 事件驱动**：健康。midiBrave 走外部恰好验证了这层设计——audio 只消费 mapping 输出，换音源只需在 audio 加 samplePlayer engine，总线/混响/昼夜宏/renderer 全不动。**无需为音源后端改架构。**
- **economy（每树 observer）+ agent（规则/LLM 流水线）+ master（policy/llm）**：结构正确。单树计分（无跨声部）是能力缺口不是架构缺陷——§2 P3 在现有层内加一条规则即可，不用重构。
- **唯一值得新增的架构件** = §1 的评测/遥测层，与 gameplay 解耦独立存在。

**明确不做**：不重写内核、不换事件模型、不改分层边界。本会话的四个 P0/P1 修复已证明「在现有架构内补执行器」就能把决策层激活——继续这条路，别推倒。

### 3.1 要不要上 Unity / 换引擎？（江南 2026-07-20 提）

**结论：不上 Unity，留在 Web；渲染技术是可延后的可换层，等视觉方向定了再选。**

分层体检的关键事实——**renderer 已经是隔离层**：world→renderer 只通过 snapshot 接口喂数据，
renderer 不反向依赖内核。这意味着渲染技术（canvas 2D → WebGL/其它）和音源一样是**可整体替换的一层**
（midiBrave 走外部已经证明 audio 层能换，renderer 同理）。所以「用什么渲染」不是现在必须押的架构赌注。

**为什么不是 Unity：**
- **核心价值引擎无关**：world 仿真、事件驱动计分、agent/LLM、mapping 全是纯 JS 逻辑，Unity 的物理/3D/粒子帮不上；换引擎要重写这套（含 192 个测试），净亏。
- **产品形态是「可分享的 2D 生成式音乐生态」**，不是重物理/重输入的 3D 游戏。它的价值一半在机制、一半在**零安装可分享**（一个网页链接，契合 Twiddle 妙搭/lark-apps 的分发路径）。Unity = 构建/安装摩擦、对分享型网页玩具是退步。
- **LLM 接入**：浏览器 fetch 到 bird_agent 是现成的；Unity 里做同样的事更绕。
- Unity 的强项（3D 物理、原生/主机/VR、资产管线）**与本产品诉求不重叠**。

**如果视觉野心超出 canvas 2D，Web 内的升级路径（不是 Unity）：**
- 2D 精灵/粒子/着色器要 GPU 加速 → **PixiJS**（2D WebGL）；
- 真要 3D 空间 → **Three.js / PlayCanvas**。
- 两者都保住「零安装可分享 + 现有逻辑核」，且因 renderer 已隔离，换渲染层是**受控改动**，不碰 world/mapping/audio/计分。

**对当下的含义**：near-term 的重活（§1 评测器 + §2 机制）全是引擎无关的，架构不构成阻塞——可以放心先推进逻辑核，
渲染技术的决策留到**视觉/玩法方向定了之后**再做（这也是「先不做 UI」成立的底气：架构已把这步解耦成可延后的换层）。

## 4. 【前端 UI】产品感的主战场

现状：renderer 是 duotone-riso 占位（canvas 手绘线条树+圆点鸟+昼夜渐变），美术四方向比稿（studies/art-directions）已产出未选定。**产品「好玩/好看」的体感几乎全在这层，目前投入最少。**

**建议先做一次 UI/交互审计**（派只读调查），产出：玩家实际看到什么、能操作什么、「生态→音乐」的因果是否可读。已知素材：Phase 4 zoom 特写（docs/phase4-interaction-design.md）、MIX 面板（已做）、决策时间线面板、四方向美术比稿。

**候选方向**（对齐后细化）：
- 发声反馈可读性：哪只鸟=哪个声部=什么音，落枝发声的视觉-听觉绑定；
- 美术方向选定：从四比稿里定一版（或融合），替换占位 renderer；
- 交互深度：zoom 特写摆鸟（Phase 4）+ MIX 调音是否够「玩法」，还是需要更主动的干预手段。

> 前端投入大、迭代快，建议独立于机制线并行；但选美术方向是江南的审美门，需你拍板。
